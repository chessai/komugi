## 2026-09-11 — KOM-165 raised the turn cap 256 → 512; NOTHING here was regenerated

Operator: the KOM-165 implementation task (advisor session, user chessai).

`observation.MAX_TURNS` went 256 → 512 and `PLANE_MAP_VERSION` 2 → 3. That
changes the VALUES of exactly two planes — 115 (turn clock) and 120 (progress
clock), whose denominator is the cap — and nothing else in the map: no plane
changed index, source or meaning. All three fixtures in this directory
(`observation_g1.json`, `observation_g2.json`, `pmv1/`) are therefore left
**byte-identical**, still carrying plane map 2 and the 256-ply cap, and the
tests compare against them through an exact rescale instead:

- `tests/encoding/test_observation_goldens.py::rescaled_to_golden_cap`
  multiplies the replayed planes 115 and 120 by `MAX_TURNS / GOLDEN_CAP` before
  digesting. Both caps are powers of two and every value is `k / cap` for an
  integer `k` below the cap, so the rescale moves the float32 exponent and no
  mantissa bit: the digests are compared bit for bit, with no tolerance.
- `tests/rules/test_observation_map.py::_rescaled_to_pmv1` does the same for
  plane 115 over the pmv1 capture (plane 120 is outside pmv1's 0-117 range).
  KOM-002's invariant P1 is therefore NOT amended: planes 0-114 and 116-117 are
  still bit-identical to `main@29213f2`, and plane 115 gains the stronger pin
  that it is a pure rescale of pmv1's. This is KOM-165 design review F4.
- Both tests assert the precondition rather than assume it: no golden ply
  reaches 256. Past that ply the frozen side is clipped to 1.0 while this one is
  not, and the rescale would stop being exact — the assertion fails with that
  explanation and names regeneration as the fix.

If these fixtures are ever regenerated at plane map 3, the rescale helpers, the
`GOLDEN_CAP` / `PMV1_MAX_TURNS` constants and the `GOLDEN_PLANE_MAP_VERSION`
allowance in `test_manifest_declares_its_source` all come out together, and a
new dated entry replaces this one.
